1. What the project is and what it should do best

Codepedia is a bilingual Romanian/English lead-generation and portfolio website for a small full-stack development studio. It combines a public marketing site, localized case studies, a contact funnel, and a private Supabase-backed CMS/lead inbox.

At its best, the project should do four things extremely well:

  1. Convert qualified visitors: explain the offer, show credible work and pricing, and reliably deliver every inquiry to the studio.
  2. Publish safely: let an administrator preview, validate, publish, rename, reorder, duplicate and unpublish content without partial writes, broken images, duplicate URLs or stale public pages.
  3. Earn trust: be fast, accessible, localized, privacy-accurate, SEO-canonical and resilient when a dependency is degraded.
  4. Be recoverable: a new environment must be reproducible from versioned migrations, seeds, Storage policy and documented deployment steps.

3. Critical and high-priority findings

P0 CriticalThe database cannot be recreated reliably from the repository

DATA_MODEL.sql is still the documented base schema, but it lacks projects.next_title_ro/en, leads.source, the rate-limit table/function, integrity constraints/triggers, and all Storage bucket/policy setup. Conversely, the first files under supabase/migrations/ are ALTER migrations that assume the base tables already exist; the save RPC then references the absent next_title_* columns. A normal clean migration run therefore has no complete starting point.

Impact: disaster recovery, staging, contributor onboarding and a fresh Supabase project can fail or silently differ from production. The project-media bucket and policies are still manual/undocumented infrastructure.

Fix: capture the complete current remote schema as an initial migration, add every subsequent migration in order, version Storage bucket/policies, add seed data, and prove it with an automated local supabase db reset test.

P1 High · regressionReplacing an image can break the currently published page before Save

AdminImageUpload.vue:42–60 uploads the replacement and immediately deletes previousPath. The project database row is updated only later when the editor Save button calls the RPC. If the administrator uploads a replacement and closes the page, hits Back, loses connectivity or the save fails, production still points to the now-deleted old file.

Fix: never delete the old asset from the upload component. Persist the new project transaction first, then enqueue old unreferenced assets for verified cleanup. Track references rather than assuming one URL belongs to one row.

P1 High · regressionDuplicated projects share media; editing or deleting a copy can damage the original

admin/projects/index.vue:95–135 copies project and child database rows but reuses all cover, hero and gallery URLs. Deletion later removes those shared Storage keys (:83–87), and replacing an image in either copy deletes the shared old key. Duplication is also multi-step and ignores child-select/insert errors, so a partially copied project can be left behind.

Fix: make duplication one server-side transaction and either physically copy each Storage object into the new project namespace or introduce a media table with reference counting. Cleanup must delete only assets with zero references.

P1 HighSlug redirects are written but never executed

The new save_project RPC inserts rows into redirects, but no server route or middleware reads that table. Repository-wide search finds only locale redirect middleware. Renamed published URLs therefore still return 404 after caches expire.

There is also an edge case: renaming and unpublishing in one save creates a redirect to an unpublished destination, which would redirect to a 404 even after a redirect handler is added.

Fix: add tested request middleware that normalizes the path, looks up an exact allow-listed redirect, prevents loops, applies 301/308, and caches safely. Create redirects only when the destination is public, or hold them until publication.

P1 HighLocalized slugs can collide across columns and both language routes accept the wrong slug

The database makes slug_ro unique and slug_en unique separately, but does not prevent one project's Romanian slug from equaling another project's English slug. server/api/projects/[slug].get.ts:28–33 queries both columns with OR and calls maybeSingle(); a cross-column collision produces multiple rows and a 500.

Even without a collision, both /proiecte/{slug_en} and /en/work/{slug_ro} resolve, creating duplicate localized pages. The locale-switch fix only produces the preferred link; it does not reject or redirect non-canonical paths.

Fix: resolve by current locale, enforce a global slug namespace (or allow overlap only across the same project), and 301 every wrong-locale slug to its canonical route. Add collision and canonicalization tests.

P1 HighAdmin publishing does not invalidate the public SWR cache

nuxt.config.ts:46–52 caches home/API responses for 60 seconds and case studies for 300 seconds. Admin writes go directly from the browser to Supabase; no code calls a purge/revalidation endpoint. A corrected page remains stale, and an urgently unpublished or sensitive case study can remain publicly served for up to five minutes.

Fix: route CMS mutations through authenticated server endpoints/RPC orchestration, then purge all affected API and page cache keys. Treat unpublish/delete as immediate invalidation.

P1 Launch blockerThe live content is visibly unfinished

The current live data has three published case studies but zero cover, hero or gallery images. Both services have null prices and the public UI prints de la [ X ] EUR / from [ X ] EUR. Placeholders are intentional development fallbacks, not a credible final portfolio.

Fix: upload optimized real case-study media with meaningful bilingual alt text, enter approved pricing or replace the placeholder with honest “price on request” copy, and complete a content/legal review before launch.

4. Medium-priority correctness, privacy and operational issues

P2 MediumGoogle Analytics still loads before consent when an ID is configured

analytics.client.ts:73 calls initGa() whenever gaId exists, regardless of consent. Consent Mode defaults storage to denied, but the Google script is fetched and gtag('config') is called. That is “advanced consent mode,” not the privacy policy's plain-language promise that Google Analytics is used only after explicit consent.

The E2E test does not verify this: its environment deliberately has empty analytics IDs, and it clicks Accept before checking requests. Either defer loading until analytics consent or explicitly adopt/document advanced consent mode after legal review, then test with dummy configured IDs and blocked external requests.

P2 MediumThe privacy policy does not match data processing

  • Rate limiting stores raw IP addresses in lead_rate_limits. Cleanup only runs on a later lead attempt; if traffic stops, an entry can remain indefinitely, contradicting “temporarily (10 minutes).” Use a keyed HMAC of the IP and scheduled TTL cleanup.
  • When enabled, Resend receives the full inquiry by email, but Resend is not listed as a processor/recipient.
  • Actual analytics/marketing cookie names and retention are not described, and the update date predates these implementation changes.

P2 MediumLead notification is not production-ready

The current local environment has no RESEND_API_KEY, the sender remains onboarding@resend.dev, and notification failures are swallowed without logging, retry or alerting. The lead may exist only in the admin inbox with no one aware of it.

Fix: verify a Codepedia sending domain, configure production secrets, log provider message IDs, queue/retry failures, alert on repeated failures, and add a safe deployment smoke test.

P2 MediumPublished-project validation is incomplete and exists only in the browser

The shared validator requires a few Romanian text fields and two gallery images, but does not require cover/hero images, meaningful alt text, context body, solution content, facts or steps. More importantly, the RPC validates only authorization and slug shape; a stale or direct authenticated client can bypass all browser validation and publish incomplete data.

Fix: enforce publication invariants in the RPC/database and return structured field errors. Validate every child collection and both localized variants according to an explicit publishing policy.

P2 MediumSeveral CMS writes still fail partially or report false success

  • Project reordering uses parallel updates and ignores each returned error.
  • Service + service-item saving is sequential and can stop after partially committing.
  • FAQ reorder ignores the upsert result and then calls markSaved(), so a failed persistence attempt can suppress the unsaved-changes warning.
  • Lead status, notes and archive operations ignore update errors; notes can display “Saved” after failure and archive navigates away regardless.
  • Project duplication is multi-step, non-transactional and silently ignores child errors.

Move compound operations into RPCs/server transactions and make every UI state derive from checked results.

P2 MediumCMS settings are still partly decorative

The admin saves meta_title_*, meta_description_*, footer_line_* and copyright_year, but public components do not read them. next_opening_*, concurrent_projects and og_image_path exist in the schema/types but are not fully editable/rendered. Homepage SEO, footer text, copyright and organization URL/logo remain hardcoded.

P2 MediumA cold Supabase outage still takes down the public site

The added SWR cache reduces frequency but does not provide a durable fallback. /api/home, projects and sitemap throw a generic 500 on database errors. An empty/cold cache during Supabase or network failure leaves the marketing site unavailable. Add stale-on-error behavior, monitored fallback content or deployment-time snapshots.

P2 MediumAccessibility fixes are incomplete

  • Most admin fields display text in div/span elements instead of associated label elements, so inputs lack accessible names.
  • Drag-only ordering has no keyboard controls or screen-reader announcements.
  • The burger publishes aria-expanded but no aria-controls.

P2 MediumImportant admin/product features remain absent

There is still no draft preview despite preview_token, no “View on site” action, no page for authenticated /admin, no revision/rollback history, no Ctrl/Cmd+S, and incomplete audit metadata outside projects. The server logs confirm /admin has no matching Vue route; unauthenticated users happen to be intercepted and sent to login.

P2 MediumSecurity headers are not configured in the repository

No Content-Security-Policy, Referrer-Policy, Permissions-Policy, X-Content-Type-Options or frame restriction is defined in Nuxt/Vercel configuration. The local response also exposes X-Powered-By: Nuxt. Add a tested production header policy; the inline Meta bootstrap will need a nonce/hash or a non-inline loader.

5. Lower-priority quality and performance issues

  • Image pipeline: MIME and 8 MB checks are an improvement, but dimensions, decode validity and aspect are not checked; originals are not resized/converted; removing one gallery slot can leave an orphan.
  • Bundle: the largest client chunk remains about 301 kB raw / 87 kB gzip, consistent with the globally installed Supabase client. Public pages only need server APIs; scope the browser Supabase client to admin/auth if possible.
  • Tooling drift: local Node 22.17.0 is below the declared ≥22.19.0 engine, and npm ls reports several extraneous Sharp/WASM packages. Use the same pinned patch release in local development and CI, then verify from a clean npm ci.
  • Lint quality: 98 warnings means lint exists but does not yet enforce a clean baseline. Fix the warnings and run CI with --max-warnings=0.
  • SEO enhancements: add canonical redirects for wrong-locale slugs, x-default alternates, optional FAQ structured data, and derive OG/Organization URLs from siteUrl.
  • Analytics correctness: Meta sends only the initial PageView; explicit route-change tracking and conversion events are absent.

7. Recommended remediation order

  1. Make the database reproducible: canonical base migration, Storage policy, seed, local reset test.
  2. Stop media data loss: remove pre-save deletion, fix duplication ownership/reference handling, add cleanup jobs.
  3. Finish URL correctness: consume redirects, prevent cross-column slug collisions, canonicalize locale routes.
  4. Move publishing behind a server boundary: authoritative validation, atomic compound operations, checked errors and immediate cache invalidation.
  5. Finish the contact operation: verified Resend sender, alerts/retries, accurate privacy policy, privacy-preserving rate-limit keys.
  6. Complete launch content: real images/alt text, pricing, legal identity/review and English copy review.
  7. Close QA gaps: isolated Supabase integration tests, authenticated admin E2E, lead API tests, configured-consent tests, accessibility automation, E2E in CI.
  8. Then add product improvements: draft previews, revision history/rollback, media library, lead search/export/CRM integration, analytics conversions, health/error monitoring and backup-restore drills.

8. Suggested acceptance gate before launch

The site should not be called launch-ready until all of the following are demonstrated:

  • A blank Supabase project can be created from versioned files only.
  • Authenticated E2E proves create → preview → publish → rename → redirect → unpublish → delete.
  • Replacing/duplicating/deleting media cannot break another project or an unsaved published record.
  • Unpublished content disappears immediately from page and API caches.
  • A real lead is stored and a monitored notification is delivered from the verified domain.
  • Consent tests run with GA/Meta IDs present and prove the chosen legal behavior before and after withdrawal.
  • Real case-study images and final service pricing/copy are present in both languages.
  • Typecheck, unit, lint with zero warnings, DB integration, accessibility, E2E, build and dependency audit all pass in CI.

Bottom line: the remediation work was real and materially improved the project. The current danger is assuming that green type/unit/build/smoke checks prove the CMS and deployment path. They do not yet cover the areas with the highest remaining risk: schema reconstruction, authenticated writes, media ownership, redirects, cache invalidation, lead delivery and configured analytics.
