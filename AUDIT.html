00 Premisa

What this project is, and what it is for

Read the repo end to end, the intent is unusually clear — worth stating plainly, because several findings below are only bugs relative to it.

A sales instrument, not a brochure

Codepedia is a two-to-three person studio in Chișinău. The site has exactly one job: convince a prospect who has never heard of you that you build serious software, then capture them in the contact form. Everything else — the bilingual routing, the case study template, the admin — exists to serve that single conversion.

The site is itself the portfolio piece

For a studio that sells web work, the site is the strongest sample in the deck. That is why the pixel-fidelity rule and the Lighthouse ≥ 95 target are not vanity: a slow or sloppy site is a counter-argument to the pitch. It also raises the stakes on P3-1 — half a megabyte of database client on a marketing page is the kind of thing a technical prospect notices.

The admin exists so nobody has to redeploy to add a project

The whole point is that a non-engineer can add a case study, publish it, and see it live. That makes the admin's silent failures the most expensive class of bug in the codebase — worse than an equivalent bug on the public site, because there is no one watching the console when a lead's answer gets dropped or a project gets duplicated.

What holds up

The design system is genuinely single-source — no hardcoded colors anywhere. The RO-fallback content model (*_ro required, *_en optional) is the right call for a bilingual studio that will always write Romanian first. Row-level security is correctly designed: public read only for published rows, writes gated behind an app_users membership check that a self-signup cannot satisfy. And the TODO.md discipline held — every missing price and result figure still renders as [ X ] rather than a plausible invention.

01 Pierdere de date

Seven paths that destroy or discard content with no error shown. Fix these before anything else.

Data loss and silent no-ops

Each of these fails quietly. The admin sees "Salvat" and believes the work was saved.

P0-1

Renaming a slug duplicates the project instead of renaming it

The editor saves with upsert(..., { onConflict: 'slug_ro' }). If the admin edits the slug field, the conflict target no longer matches any existing row, so Postgres inserts. You end up with two projects: the original at the old slug, still live, and a full copy at the new one — with the child rows (facts, steps, stats, images) attached only to the new record.

app/pages/admin/projects/[slug].vue : 139, 175

Fix Key the write on id, not the slug. Insert when new, update by id when editing, and write a redirects row for the old path (see P1-6).
P0-2

Child rows are deleted before the replacement insert is known to succeed

Every save does delete().eq('project_id', …) then .then(() => insert(…)) for facts, steps, stats and images. Two problems: the delete's own error is never read, so a failed delete still proceeds to insert and duplicates every row; and if the insert fails — dropped connection, a constraint, an expired token — the old rows are already gone. The case study loses its entire content body with no way back.

app/pages/admin/projects/[slug].vue : 188–254

Fix Move the whole save into one Postgres function called via rpc() so it runs in a single transaction. Short of that, check the delete's error before inserting.
P0-3

The contact form asks "how did you hear about us" and throws the answer away

ContactForm collects source and posts it. The server declares it on LeadBody — and never inserts it. There is no source column in leads at all. Every visitor who fills that field has their answer discarded, 100% of the time. It is the one attribution question on the whole site.

ContactForm.vue : 14 · server/api/leads.post.ts : 14 · DATA_MODEL.sql : 200

Fix Add the column, insert the value, show it in the lead detail view. While there: leads.utm exists and is never populated either — capture the query string on submit.
P0-4

Half the Settings screen edits fields the site never reads

footer_line_ro/en, copyright_year, meta_title_* and meta_description_* are all editable in /admin/settings and saved to the database. Nothing renders them. SiteFooter uses t('footer.copyright') from the locale JSON; the homepage uses t('seo.home.title'). An admin who changes the site's meta description sees a confirmation and gets no change.

Three more columns — og_image_path, next_opening_ro/en, concurrent_projects — exist in the schema and the generated types and are neither editable nor rendered. The OG image control is a hardcoded label reading "disponibil după conectare".

app/pages/admin/settings/index.vue · SiteFooter.vue : 21, 27 · app/pages/index.vue : 5

Fix Pick a direction per field and commit: either wire it into the render path, or take the control out of the UI. A control that does nothing is worse than a missing one.
P0-5

Empty gallery slots are saved as image rows with an empty path

The editor seeds two blank gallery slots. On save it inserts path: img.path ?? '' for each — and project_images.path is not null, so an empty string passes. A project saved without gallery uploads gets image rows that render <img src=""> on the case study, which browsers resolve to the page URL and re-request.

app/pages/admin/projects/[slug].vue : 246

Fix Skip slots with no uploaded path. Add a check (path <> '') constraint so the class of bug cannot recur.
P0-6

Saving the FAQ screen resets every publish date, and nothing can be deleted

published_at: item.published ? new Date().toISOString() : null — so any save re-stamps every published question with today's date. The projects editor gets this right (existing.published_at ?? now); the FAQ screen does not. Separately, there is no delete: questions can be added and edited forever, never removed. Drag reordering fires N sequential updates with no error handling, so a failure mid-way leaves the order half-applied.

app/pages/admin/faqs/index.vue : 44, 72–75

Fix Preserve the existing timestamp, add a delete with confirmation, and batch the reorder into a single upsert.
P0-7

DATA_MODEL.sql no longer matches the live database

next_title_ro and next_title_en exist in the generated types, in the seed script, in both API queries and in mapProject — and are absent from DATA_MODEL.sql. Applying that file to a fresh Supabase project produces a database on which every project query returns a 500. There is no migrations directory; the schema file is being hand-maintained and has already drifted.

Two related gaps: the project-media storage bucket's policies are not in the file at all, so a rebuild has no defined upload authorization; and app_users.role distinguishes admin from editor while is_admin() only checks row existence — every editor is a full admin.

DATA_MODEL.sql : 23–61, 230–287

Fix Move to supabase/migrations/ and generate the schema file from the database rather than the other way round.
02 Public

Visible to prospects and to Google. Two are deployment blockers.

Bugs a visitor or a crawler will hit

Ordered by how much they cost on the way to a lead.

P1-1

Sharp is compiled for Windows; Vercel runs Linux

The build prints it outright: "sharp binaries have been included in your build for win32-x64. Make sure you deploy to the same architecture." There is no nitro.preset and no vercel.json, so @nuxt/image will ship a binary the runtime cannot load. Every project image breaks on the first deploy.

Fix Build on Vercel rather than locally, and set the image provider explicitly so Vercel's own optimizer handles resizing instead of a bundled IPX.
P1-2

Canonical and hreflang tags fall back to localhost:3000

i18n.baseUrl reads NUXT_PUBLIC_SITE_URL with a localhost default. That variable appears nowhere else in the repo — not in .env, not in .env.example, not in the README. If it is not set in the Vercel dashboard at build time, every canonical and alternate link in production points at localhost. RESEND_API_KEY has the same problem: undocumented, and unset it silently disables lead notification emails entirely.

nuxt.config.ts : 10, 57 · .env.example

Fix Add both to .env.example. Fail the build loudly when the site URL is missing rather than defaulting to localhost.
P1-3

Every project image on the site has an empty alt

MediaFrame defaults alt to '' and no caller passes one. Covers, hero screenshots, gallery — all empty. The alt text exists: it is in the database as cover_alt_ro, hero_alt_ro, alt_ro, the admin form marks those fields required, and mapProject reads them — only to wrap them in brackets as the hatched-placeholder caption. The real value is written, stored, mapped, and then not used for the one thing it is for.

MediaFrame.vue : 11 · HomeWork.vue : 30 · CaseStudyHero.vue : 38

Fix Return the raw alt alongside the bracketed label from mapProject and bind it.
P1-4

Switching to English on a case study keeps the Romanian slug

switchLocalePath('en') reuses the current route params, so /proiecte/saas-logistica becomes /en/work/saas-logistica — the Romanian slug in an English URL. It resolves, because the API matches either slug column, which is exactly what makes it a duplicate-content problem: the same page is reachable at two English URLs, and the one the sitemap advertises (/en/work/{slug_en}) is not the one your own header links to.

HomeWork gets this right — it builds the link from the locale-aware slug. Only the case study header is wrong.

CaseStudyHeader.vue : 28, 36 · server/routes/sitemap.xml.ts : 40

Fix Pass the mapped slug into switchLocalePath explicitly, the way the homepage grid does.
P1-5

The language switcher only remembers your choice on the homepage

SiteHeader writes the codepedia_locale cookie on click. CaseStudyHeader does not. Switch to English on a case study, navigate home, and geo-IP silently switches you back to Romanian — which is precisely the override the cookie exists to prevent.

CaseStudyHeader.vue : 27–41 vs SiteHeader.vue : 6–14

P1-6

The redirects table exists and no code reads it

A table designed for exactly one purpose — keeping old URLs alive when a published slug changes — with a from_path, a to_path, a status code, RLS policies, and zero references anywhere in app/ or server/. Combined with P0-1, renaming a published project both duplicates the record and permanently breaks every existing link to it.

Fix A server middleware that looks up the path and issues the stored status, plus an automatic row whenever a published slug changes.
P1-7

The admin can publish a project at a URL that returns 404

The slug field is free text with no validation or slugification. The public API rejects anything that is not ^[a-z0-9-]+$. Type Proiect Nou or anything with a diacritic, tick "Publicat", and the admin shows a published project whose page does not resolve. The editor's own "Vezi pe site" link goes to the 404.

Related: the create route is the literal path /admin/projects/nou, so nou can never be a real slug — an unguarded collision.

app/pages/admin/projects/[slug].vue : 8, 129 · server/api/projects/[slug].get.ts : 19

P1-8

The homepage title and description do not update on language switch

useSeoMeta is called with the resolved strings t('seo.home.title') rather than getters. Client-side navigation between / and /en reuses the page component, so setup does not re-run and the meta tags keep the previous locale's text. The case study page does it correctly with () => getters.

app/pages/index.vue : 4–12

P1-9

The lead rate limiter does not survive a serverless cold start

useStorage('leads-rate-limit') with no mount configured in nitro.storage resolves to in-memory. On Vercel each function instance keeps its own counter, so the three-per-ten-minutes limit is effectively unenforced. The honeypot is doing all the real work.

The same handler accepts unbounded field lengths — no maximum on name, message or company — and stores the translated budget label rather than a stable key, so the same budget band lands in the database as two different strings depending on the visitor's language.

server/api/leads.post.ts : 37–46, 55

P1-10

The locale redirect sets no cache headers

The 302 on / and /en varies by cookie and by geo-IP header, and sends neither Cache-Control nor Vary. Nothing caches it today because those two routes have no route rule — but that is an accident, not a guard. The first person who adds ISR to the homepage will pin one audience's redirect for everyone.

server/middleware/locale-redirect.ts : 15–17

03 Conformitate

The consent system is well-built and incomplete in two specific ways that matter legally.

Consent and accessibility

The architecture is right — inert without IDs, cookie-backed, reopenable from the footer. These are gaps in it, not objections to it.

P2-1

Consent Mode v2 is missing three of its four signals

The plugin sets analytics_storage only. Consent Mode v2 requires ad_storage, ad_user_data and ad_personalization as well — and without wait_for_update, gtag may fire before the stored consent is read on a slow first paint. The documentation calls this Consent Mode v2; as written it is v1.

app/plugins/analytics.client.ts : 20–22, 34–36

P2-2

Marketing consent can be given but not withdrawn

injectMetaPixelIfConsented guards on a metaInjected flag that is never cleared. Once the pixel is on the page, revoking marketing consent updates the cookie and changes nothing — fbq keeps running and its cookies stay set for the rest of the session. GDPR treats withdrawal as needing to be as easy as consent.

No first-party analytics cookies are cleared on reject either.

app/plugins/analytics.client.ts : 39–41, 58–61

Fix On withdrawal, clear the vendor cookies and reload. A reload is the honest way to guarantee third-party scripts are actually gone.
P2-3

The privacy policy is noindex and absent from the sitemap

robots: 'noindex, follow' on the one page whose entire purpose is public transparency, and it is the page the cookie banner links to. The sitemap also omits it and carries no x-default hreflang or lastmod on any entry.

app/pages/confidentialitate.vue : 9 · server/routes/sitemap.xml.ts : 16

P2-4

Accessibility gaps that a Lighthouse ≥ 95 target will surface

No skip-to-content link in any layout. scroll-behavior: smooth is set with no prefers-reduced-motion guard. The cookie banner is a fixed overlay with no role="dialog", no focus move, and no focus trap. Contact form errors are plain paragraphs with no aria-invalid or aria-describedby tying them to their inputs. The mobile menu button sets aria-expanded but no aria-controls. Every drag-to-reorder list in the admin is mouse-only.

Separately, the signal button contrast is 3.13:1 against paper — below AA. Noted as a deliberate match to the prototype and left alone; flagged here only so it does not read as an oversight when the Lighthouse report lands.

main.css : 32 · CookieBanner.vue : 22–26 · ContactForm.vue : 75, 88

04 Performanță

The Lighthouse ≥ 95 target is currently out of reach for one reason.

Weight and rendering

P3-1

508 KB of Supabase client ships to every marketing page

The entry chunk is 508 KB of the 675 KB total client JavaScript. Grepping it turns up @supabase/auth-js, @supabase/ssr, realtime-js and the GoTrue client — the whole SDK, on a homepage that fetches everything through /api/* server routes and needs no database client in the browser at all. It is there because @nuxtjs/supabase registers a global plugin.

Recorded as a deliberate deferral. Worth restating that it is the single largest obstacle to the stated Lighthouse target, and the fix is bounded: scope the Supabase plugin to /admin routes.

P3-2

NuxtImg is used without dimensions, sizes, or lazy loading

MediaFrame renders <NuxtImg> with only src, alt and classes. No width/height means layout shift on every project card; no sizes means no responsive srcset, so mobile downloads the 1600×900 hero. The aspect-ratio class prevents the worst of the CLS but does not replace intrinsic dimensions.

MediaFrame.vue : 30–35

P3-3

The homepage is fully server-rendered on every request

routeRules caches the case studies and the API routes but not / or /en — necessarily, because the geo redirect runs there. The result is that the most-visited page is the only uncached one. Moving the redirect decision to the edge would let the homepage shell cache like everything else.

nuxt.config.ts : 24–30

05 Proces

Nothing enforces the rules the project sets for itself.

Tooling and dead weight

P4-1

"TypeScript strict, no any" is a rule with no enforcement

nuxi typecheck exits immediately: "A type checker is required." There is no vue-tsc, no typecheck script, no ESLint config, and no CI workflow anywhere in the repo. Strict mode is on in the generated tsconfig and the code does hold to it — a grep for any, @ts-ignore and stray console.log across app/, server/ and shared/ comes back empty. That is discipline, not tooling, and discipline does not survive a second contributor.

P4-2

536 lines of superseded content files nobody imports

app/data/projects.ts (391 lines), services.ts (94) and faq.ts (51) are the step-2 hardcoded content, orphaned when the pages moved to Supabase. They are a second copy of the case study text that will silently diverge from the database. settings.ts survives only to feed a contact email into the JSON-LD block — the same value site_settings.contact_email already holds.

Fix Delete the three, and read the JSON-LD email from the settings API like every other consumer.
P4-3

The e2e suite cannot run without production credentials

playwright.config.ts runs npm run build as its web server, and the smoke tests navigate to /proiecte/saas-logistica — a real row in the live database. There is no fixture or seeded test project, so the suite depends on production content staying exactly as it is. Coupled with the absence of CI, the tests only ever run when someone remembers to run them.

P4-4

Smaller sharp edges

No unsaved-changes guard on any admin form — navigating away loses everything silently. The project duplicate action swallows every error and just stops. Deleting a project leaves its uploaded images in storage forever. robots.txt does not disallow /api/. The Supabase project reference is hardcoded in nuxt.config.ts's image domains. The preview_token column is generated for every project and read by nothing, while the editor displays "Vezi ca draft — token disponibil după prima salvare", promising a feature that does not exist.

06 Extindere

Ordered by effect on the one thing the site is for.

What to build next

Most of these are half-built already — the schema anticipated them and the code stopped short.

Schema ready
Redirect engine

The table is designed and empty. A middleware plus an automatic row on slug change closes P1-6 and makes renaming a published project safe for the first time.

Schema ready
Draft preview links

preview_token already exists on every project. A tokenized route lets a client review an unpublished case study — the workflow the admin UI already advertises.

Schema ready
Lead attribution

Capture UTM parameters into leads.utm and add the missing source column. Without them there is no way to tell which channel produces business.

Missing
Project ordering in the admin

sort_order controls the homepage grid and is unreachable from the interface. The order of the three case studies is the site's strongest editorial lever.

Missing
Add and remove rows in the project editor

The gallery is frozen at two slots and the facts list at whatever exists — despite a label reading "minim 2". Steps and stats have add buttons; facts and gallery do not.

SEO
FAQPage and BreadcrumbList structured data

A published Q&A section already renders from the database. FAQPage markup is close to free and earns expanded search results; Organization alone is leaving that on the table.

Decision
A /proiecte index page

TODO.md raises this as open. The grid is designed for three; a fourth case study forces the question, and the sitemap has no listing page to point at.

Considered
Russian as a third locale

Under discussion, not decided. Worth noting that the *_ro/*_en column-pair model does not extend to a third language without a schema change — that cost should be priced into the decision rather than discovered during it.

07 Concluzie

At its best

The single change with the most leverage is not on this list as a bug: make the admin incapable of failing silently. Every one of the seven P0 findings is the same defect wearing a different costume — an action reports success while doing nothing, or something worse than nothing.

The finished version of this project

A fast bilingual site that loads in well under a second because it ships almost no JavaScript, three case studies with real screenshots and real numbers replacing the [ X ] placeholders, and an admin where every control does something visible and every save is atomic. Leads arrive attributed. Slugs can be renamed without breaking the web. The Lighthouse report is a screenshot you can put in a pitch deck.

The order I would work in

Fix the seven data-loss paths first — they are cheap and they are actively destroying work. Then the two deployment blockers (P1-1, P1-2), because nothing else matters if the first production deploy serves broken images and localhost canonicals. Then scope the Supabase plugin to the admin, which buys back most of the performance budget in one change. The accessibility and consent items are a contained afternoon after that. Everything in section 06 is genuinely optional until the content in TODO.md arrives.

One thing to keep doing

The placeholders held. Every missing price still reads de la [ X ] EUR, every missing result figure is still bracketed, and the seed script declines to invent a single number. For a studio whose entire pitch is that it does careful work, that restraint is worth more than any feature on this page.
